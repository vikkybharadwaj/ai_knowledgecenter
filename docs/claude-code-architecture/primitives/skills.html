Skills (& what “routines” really means)

Reusable instructions, procedures, and optional scripts — packaged in a folder, loaded on demand. The most flexible way to extend a session. If you’ve heard the word “routines,” this is almost certainly what you meant.

Analogy — a recipe card in a binder. Its title is always visible on the spine (cheap), but you only pull the full card when you’re cooking that dish. The model does the cooking with tools it already has — the card just tells it how.

“Routines” is not an official term Zero hits in the docs. A saved, repeatable procedure = a skill (custom slash commands were merged into skills). Orchestration across many agents = a dynamic workflow. A default voice/format = an output style.

Mechanism — progressive disclosure

A skill is a directory with a SKILL.md (YAML frontmatter + markdown body). The folder name becomes the /command. The design principle is progressive disclosure:

always
name + description
~tiny cost, sits in context so Claude knows the skill exists
on invoke
the body
full instructions load only when used or matched
if referenced
scripts / reference files
loaded/executed only when the body points to them
Key frontmatter & who can invoke

description (drives auto-invocation), allowed-tools (pre-approve tools while active), disable-model-invocation, user-invocable, context: fork + agent (run in a subagent), model, effort, paths (glob-gated).

  • Both (default): you type /name OR Claude auto-loads by description.
  • User-only (disable-model-invocation: true): for side-effecting actions like /deploy.
  • Model-only (user-invocable: false): passive background knowledge.

Dynamic context: !`cmd` runs a shell command before Claude sees the body and inlines the output. Substitutions: $ARGUMENTS, ${CLAUDE_SKILL_DIR}, ${CLAUDE_SESSION_ID}.

Lives at .claude/skills/<name>/SKILL.md (project, committed) or ~/.claude/skills/ (personal). Precedence: Enterprise > Personal > Project; plugins namespaced.

When to reach for it

✓
You paste the same checklist/procedure a third time.
✓
A CLAUDE.md section has become a procedure rather than a fact — move it out so it costs nothing until used.
✓
You want a reusable /command shared with the team via the repo.

When not to

✕
A must-run guardrail → hook (skills are discretionary).
✕
An always-needed fact → CLAUDE.md.
✕
Reaching an external system → MCP (a skill only knows how to use tools that already exist).

Best practices

★
Front-load the description with the use case + trigger keywords — a weak description means the skill never fires.
★
Keep SKILL.md under ~500 lines; push API specs/examples into referenced files (progressive disclosure).
★
Set disable-model-invocation: true for anything with side effects (deploy, commit, send).
★
Reference bundled scripts via ${CLAUDE_SKILL_DIR} so paths resolve at any scope.
Security allowed-tools grants permission silently while the skill is active, and the !`...` shell injection runs arbitrary commands. Review project skills before trusting a repo. Org-wide kill switch: "disableSkillShellExecution": true.
