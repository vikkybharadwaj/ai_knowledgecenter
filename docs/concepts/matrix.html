The comparison matrix

The one table to return to whenever a new feature lands and you’re not sure where it fits. Read a row left-to-right to understand a primitive; read a column top-to-bottom to compare them on one dimension. Reviewed 2026-06-06.

All ten primitives, side by side

“Soft” = the model chooses whether to follow it. “Hard” = the client enforces it regardless of the model. “Who holds the plan” is the single best discriminator for the coordination primitives.

The left columns help you understand each primitive; the right ones help you use it well — Cost & footprint (what it spends — tokens, latency, context), Pairs with (how it composes with the others), and Watch out for (its characteristic failure mode).

Coordination groupings (not a ladder)

The same ten, grouped by how much coordination they add — from steering one session to orchestrating many and running unattended. It’s a map, not a ladder: go broad or deep wherever a real trigger appears. Most everyday work lives in the first two groups.

GroupGoalPrimitivesWhat changesThe trigger to reach further
Foundations Drive one session well. CLAUDE.md / memory · slash commands · the Explore→Plan→Code→Commit loop You shape soft context; no parallelism, near-zero new concepts. You keep re-typing a prompt, or pasting a multi-step playbook.
Extend a session Customize, connect, guarantee, and delegate — still within one session. Skills · MCP · Hooks · Subagents You add know-how, external reach, hard guarantees, and isolated delegation. Subagents hit context limits, or need to communicate.
Orchestrate / Operate Coordinate many agents, govern across repos — and run unattended in the cloud. Agent teams · Dynamic workflows · Worktrees + Agent view · plugins · policies · Routines (cloud) The plan leaves your single context — into a lead, a script, many sessions, or a saved cloud config a trigger runs; plus org governance. — (the widest group; here you optimize cost & trust)

Breadth vs depth

Two different kinds of scaling. Breadth = how many things run in parallel. Depth = how much sustained, single-thread reasoning & shared context a unit of work keeps. Picking the wrong axis is the most common mistake: people reach for agent teams (breadth) when they needed one deep session (depth), and vice-versa.

How to read the bars Each bar is a relative score, not a line graph — it just shows how much of that one quality a primitive has. A short bar = low, a full bar = high. So under Breadth, “One session” is nearly empty (it does one thing at a time) while “Dynamic workflows” is full (it fans out to many tasks at once). Compare bars down a column to rank primitives on that axis; compare a row’s two bars to see whether that primitive leans breadth or depth.
PrimitiveBreadth (parallelism)Depth (sustained context)Sweet spot
One session
Iterative, interconnected work that needs full shared context.
Subagents
A few isolated side-quests whose summaries feed the main thread.
Agent teams
A handful of deep, long-running peers that must coordinate.
Agent view
Many independent full sessions you supervise loosely.
Dynamic workflows
Massive fan-out of shallow, well-scoped tasks + cross-check.
Rule of thumb If the units of work don’t need each other’s context → push for breadth (workflows / agent view). If they do → keep depth (one session, or a small agent team that talks).

The soft / hard split (memorize this for the exam)

Soft · model-mediated

The model reads it and tries to comply. No guarantee. Great for guidance, terrible for guardrails.

CLAUDE.md · .claude/rules/ · skills · output styles · effort level · MCP tool choice

Hard · client-enforced

Happens (or is blocked) regardless of what the model decides. The only real guardrails.

hooks (esp. PreToolUse) · permission rules (allow/ask/deny) · managed settings

The trap Writing “never run curl” in CLAUDE.md is a request. To actually block it, use a permissions.deny rule or a PreToolUse hook. Soft text cannot enforce; only the client can.

Terminology fixes

Three pairs that sound like the same thing under different names. Two of three are not — and one word now names two different things.

“Conventions or policies — same thing?” → No.

Conventions (CLAUDE.md)Policies (managed settings)
WhatMarkdown you write that Claude readsAdmin-deployed config the client enforces
EnforcementSoft — no compliance guaranteeHard — cannot be overridden
Example“Use 2-space indentation”permissions.deny: ["Bash(curl *)"]

Docs say it verbatim: “Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude’s behavior but are not a hard enforcement layer.” (memory, settings)

“Routines” → Two different meanings — don’t conflate them.

The word now points at two things:

→
Colloquial — a saved, repeatable procedure you call “a routine” → a skill (custom slash commands were merged into skills). Orchestration across many agents → a dynamic workflow; a default voice/format → an output style.
→
Official — the feature literally named Routines: a saved config run unattended on Anthropic’s cloud on a schedule / GitHub event / API call. Not a saved procedure — a different primitive entirely.

“Rules or hooks — all the same?” → No — three things wear the word “rule.”

TermWhat it actually isNature
HooksYour code, run on a lifecycle event (PreToolUse…)Deterministic code that runs
Permission rulesallow/ask/deny strings in settings.jsonDeclarative config (deterministic), not code
Project rules.claude/rules/*.md — path-scoped CLAUDE.md-style memorySoft guidance (just modular memory)

A hook is the only one that executes your code. A permission rule is config the client evaluates. A .claude/rules/ file is just memory. Docs: “To block an action regardless of what Claude decides, use a PreToolUse hook.” (hooks)
